# inf-20100227-1433: reverse-engineering notes

Source jar: `inf-20100227-1433.jar`, SHA-256 `507cecfad21caa2e137a00c57d63ac6ebc299cb1191e703f1c49274d53e7fef3`.

Status: **supported** (`GameVersion.INF_20100227_1433.supported = true`). The server runs this build and a patched
client of this build can join: it shows the server's terrain, changes blocks in both directions, shows other players,
has chat and commands, a multiplayer menu and saved inventories. The build has its own plugin API (`api227`). The
sections below are the reverse-engineering notes that the bridge and the client are based on.

Each entry below is marked:

- **verified**: checked against the bytecode (signatures and bodies) or run in a test.
- **candidate**: the structure fits, but the bytecode has not been compared in full.

## What this build does and does not have

- **No mobs.** No mob class names or strings (Pig, Zombie, Creeper, Skeleton, Sheep). No minecarts, no signs.
- **No tile entities, no metadata, no light arrays.** Chunks hold block ids only.
- **No automatic world saving** in the original game. The menu has "Save level" and "Load level", which are stubs
  (see below).
- **No multiplayer menu.** The client mod must add it.
- **No world seed.** The terrain generator is not seeded from `level-seed` (see "Terrain").
- 289 class files (20100630 has 363). Classes are in packages (`net/minecraft/a/...`, `net/minecraft/client/...`).

**Name clash:** the jar also has a class `net/minecraft/a/a.class`. The Java compiler then reads `net.minecraft.a.a.e`
as a member of that class and cannot import it. So the 20100227 bridge reaches every game class by reflection
(`Class.forName`), not by an import. Keep this in mind for any new 20100227 code.

## Block ids

Ids come from the constructor arguments in the registry's static initializer (`net/minecraft/a/a/b/x`).
The numbering is the standard Infdev/Beta one, which the bridge's rules rely on:

- 0 air, 1 stone, 2 grass, 3 dirt, 4 cobblestone, 5 planks, 6 sapling, 7 bedrock, 8-9 water, 10-11 lava,
  12 sand, 13 gravel, 14-16 ores, 17 log, 18 leaves, 19 sponge, 20 glass, 21-36 coloured cloth, 37-38 flowers,
  39-40 mushrooms, 41-42 gold and iron blocks, 43-44 slabs, 45 bricks, 46 TNT, 47 bookshelf, 48 mossy cobblestone,
  49 obsidian, 50 torch, 51 fire.
- Names are only extracted for a few blocks (stone, wood, gravel, grass, cloth, sand). The rest of the names are
  taken from the Beta list and are not confirmed in this jar yet.
- The generator puts obsidian (49) on the lowest layer in a test world, so the bottom of the world is not bedrock.

## Terrain

- `f.a(g)` fills the 32768 block ids of one chunk with noise. Its random source is a `java.util.Random` created with
  no seed (`f` constructor), and some steps call `setSeed` with values built from the chunk coordinates.
- **Not deterministic across runs.** Two runs of the same test gave different spawn heights (76, 71, 74, 82) and a
  different block at (9,70,9). Inside one run, a loaded chunk is consistent. The cause is not traced yet.
- Consequence: `level-seed` has no effect for this build. A chunk that was never saved is generated again on the
  next start and may differ. Saved chunks keep their data.

## Save and load: the build has no working format

Verified in the bytecode:

- `net/minecraft/client/c/o.a(File)` ("Save level") opens a `FileOutputStream`, creates `net/minecraft/client/f`
  and calls `f.a()`. The stream is never written. It is closed afterwards.
- `net/minecraft/client/c/e.a(File)` ("Load level") does the same with a `FileInputStream`: nothing is read.
- `net/minecraft/a/a/a.a()` only prints "Saving level" and "Preparing level.." and builds an empty `com/a/a/a`.
- The bundled `com/a/a/` package has the tag base class and a compound class, but no reader or writer.

So this build has no save format to reuse.

**Decision (confirmed by the user): NBT.** The server writes 20100227 worlds as GZIP-compressed NBT, with the same
container and chunk tags as 20100630 (its chunk writer is class `fp`, its NBT I/O is `ap`, its tag class is `ae`):

- `worlds/inf-20100227-1433/<level-name>/level.dat`: root compound with child `Data`:
  `RandomSeed` (always 0 here, not used), `SpawnX`, `SpawnY`, `SpawnZ`, `Time`, `LastPlayed`.
- `worlds/inf-20100227-1433/<level-name>/c.<x>.<z>.dat` (decimal chunk coordinates): root compound with child `Level`:
  `xPos`, `zPos`, `LastUpdate`, `Blocks` (32768 bytes, index `x << 11 | z << 7 | y`, the same index as the game's
  chunk array), `Data` (16384 bytes of zeros, no metadata), `SkyLight` (16384 bytes of 0xFF), `BlockLight` (zeros),
  `HeightMap` (256 bytes, index `z * 16 + x`, highest solid y plus one), `TerrainPopulated` (1).
- No `Entities` or `TileEntities` tags, because this build has neither.
- The file names are our own. 20100630 names its chunk files differently (class `fp`), so a copy between the two
  builds needs the files renamed. That is a manual step, as for any world copy between builds.
- A save writes every loaded chunk. The build keeps no dirty flags, so each save rewrites all of them.

## Chunk data sent to the client

The bridge returns the 20100630 layout (`Protocol.CHUNK_RAW_SIZE` = 82176 bytes): blocks, zero metadata, full
sky light, zero block light, height map. The 20100227 client will read the blocks only, but the layout is kept so
the server code stays the same as for 20100630.

## Bridge

`server/bridge227/TWBridge227.java` and `TW227Nbt.java` (compiled by `build.sh` when `GAME227_JAR` is set; loaded
from the server jar's `bridge/` folder).

- Implemented: load, save (NBT as above), block get and set, chunk data, chunk loaded check, `isSolid`, `safeY`,
  `getHighestY`, the spawn point, time and the listener hooks.
- No-ops or empty results (this build has these features absent): mobs, minecarts, paintings, tile entities, TNT,
  riders, arrows, sounds, entity lists, scheduled ticks.
- Block rules (`isSolidId`): not solid are air, sapling, water, lava, flowers, mushrooms, torch and fire.
  Leaves are solid for `getHighestY`, and `safeY` skips them.
- `getMaxStackSize` returns 64 for every id until the game's stack sizes are extracted.

## Tests run

- Headless test (a small test program, not part of the repository): load, spawn inside the world, `setBlock` then read back,
  chunk loaded, raw chunk size 82176, block and height map in the raw data, chunk file and `level.dat` written,
  reload in a new bridge with the block and spawn kept. **All pass.**
- 20100630 regression (`Test630.java`): load, hooks applied, save. **Pass.**
- Server start with `game-version = inf-20100227-1433` (temporarily `supported = true`, then set back to false):
  starts and listens. A handshake with protocol 11 is refused (`Protocol version mismatch (server 10, client 11)`);
  protocol 10 is accepted, and the server sends the spawn chunks. `/stop` saves 81 chunk files and `level.dat`;
  a second start loads them and saves again.
- A real client join is described under "Client".

## Client

The same `TheWellosInfdevClientPatcher.jar` patches both builds: it detects the build from the jar and adds the manifest
attribute for it. Mod sources: `client/mod227/` (`TW227Client`, `TW227Launcher`), plus `TWConnection` and `TWAuth`
shared with 20100630. The build script makes `dist/inf-20100227-1433-mp.jar` when `GAME227_JAR` is set.

- **Hooks** (inserted by `ClientPatcher.createTransformer227`, no game types in their signatures):
  `net/minecraft/client/d.f()` start (game tick, runs also at the title screen), `net/minecraft/a/a/e.a(IIII)Z` end
  (block set; the method reuses its parameter slots, so the arguments are copied at its start), and
  `net/minecraft/a/a/f.a(g)` start (the terrain generator returns an empty array while connected).
- **Multiplayer button.** The title screen's disabled third button ("Play tutorial level", id 3) becomes
  "Multiplayer...". Clicking it opens an address dialog (a Swing input box; the game's screen classes cannot be
  subclassed from source because of the name clashes) and connects. Hooks: `net/minecraft/client/q.b()` end and
  `q.a(button)` start. The button is shown and enabled in the title screen; the click and dialog are not tested
  (a test would take over the real mouse). `TW227Launcher [name] --connect host[:port]` still connects at start-up.
  The game starts at its title screen without a world; after the server's login the mod creates an empty world,
  closes the menu and fills the chunk map with the server's chunks (reflection, as in the bridge). The renderer is
  told through the world's listeners (`net/minecraft/a/a/b.a(III)`), one call per 16-block layer.
- **Set-world check:** the game's `d.a(e)` reads a URL built from the applet's document base and keeps the world
  only if that check passes. The launcher's document base is a closed local port (the request fails at once, nothing
  goes to minecraft.net) and the mod sets the world field itself.
- Position: the wire uses the eye height (feet + 1.62); the game's `c/b.b(DDDFF)` takes the feet height. Fields used on
  the player (`net/minecraft/a/c/b`): `g`, `h`, `i` position, `m`, `n` yaw and pitch.
- Test aids: `-Dthewellodev.nofocus=true`, `-Dthewellodev.exitafter=<seconds>`, `-Dthewellodev.debug=true` and
  `-Dthewellodev.testplace=dx,dy,dz,id` (sets one block near the player through the game's own set-block method).
- Needs LWJGL 2 jars and natives (BetaCraft's `bin` folder works); account checks (`online-mode`) use
  `-Dthewellodev.token=<access token>`, as for 20100630 (not tested for this build).

Tested with a real client window against a scratch server (`online-mode=false`): login, spawn, the world renders
the server's terrain, a block placed by the client is applied by the server (found in the saved chunk) and echoed
back, `/setblock` on the server is stored. A ground-level screenshot of the client showed grass terrain, the
hotbar and the sky.

## Known gaps

- The multiplayer button opens an address dialog; there is no server list or in-game connect screen.
- The block names and stack sizes come from the Beta list, not from this build's registry.
- The whole world is saved on each save (no dirty flags per chunk); this may be slow for very large worlds.
- The terrain generator is seeded by the server (`TWSeed`), but the random scatter of flowers still differs between runs.
